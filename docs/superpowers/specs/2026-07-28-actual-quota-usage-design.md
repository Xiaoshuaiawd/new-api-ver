# 实际额度消耗统计设计

## 目标

在管理端使用日志统计栏中，为超级管理员增加“实际额度消耗”指标。该指标使用日志产生时记录的分组倍率还原倍率应用前的额度，支持现有历史日志，并跟随日志页面的筛选条件。

## 计算口径

只统计消费日志（`LogTypeConsume`），不纳入退款、充值、管理、错误或其他日志类型。

单条日志的实际额度计算公式：

```text
实际额度 = 日志额度 / 日志记录的 group_ratio
```

- `group_ratio = 1` 时，日志额度为 10 美元，实际额度为 10 美元。
- `group_ratio = 0.23` 时，日志额度为 10 美元，实际额度约为 43.48 美元。
- `group_ratio` 缺失、无法解析、为零或为负数时，按倍率 1 处理，即实际额度等于日志额度。
- 聚合结果允许保留小数，前端最终按货币格式显示两位小数。

## 方案选择

采用数据库侧聚合历史日志的方案：从日志 `other` JSON 中读取当时的 `group_ratio`，在查询中完成 `quota / group_ratio` 后求和。

未采用的方案：

- 新增日志字段并回填：查询性能好，但需要跨 SQLite、MySQL、PostgreSQL、ClickHouse 做字段迁移和历史回填，改动范围较大。
- Go 逐条读取并计算：数据库兼容简单，但会把匹配的历史日志全部传输到应用层，大时间范围下性能较差。

数据库侧聚合不修改日志表结构，能立即覆盖历史数据，并避免把全部日志加载到应用内存。

## 后端设计

在日志模型层增加独立的实际额度聚合函数，复用当前日志统计的筛选口径：

- 日志类型固定为消费日志。
- 支持开始时间、结束时间、用户名、令牌名、模型名、渠道和分组筛选。
- 针对 SQLite、MySQL、PostgreSQL 和 ClickHouse 生成对应的 JSON 数值提取表达式。
- 所有分支对缺失或非正倍率回退到倍率 1。

`GET /api/log/stat` 仅在当前用户角色为超级管理员时执行该聚合，并在响应中增加：

```json
{
  "actual_quota": 434782.6086956522
}
```

普通管理员和普通用户的统计响应不包含该字段，避免仅依赖前端隐藏敏感经营数据。

## 前端设计

在使用日志顶部统计栏的“期间收益”后增加一个统计徽标：

- 中文文案：`实际额度消耗`
- 英文翻译键：`Actual Quota Consumption`
- 数值使用现有额度/货币格式化能力展示两位小数。
- 仅当当前用户角色为超级管理员时渲染。
- 加载状态为超级管理员增加对应的骨架占位，避免加载完成时布局跳动。
- 补齐项目现有全部前端语言文件。

## 错误处理

- 实际额度查询失败时，日志统计接口沿用当前错误响应方式，不返回部分统计结果。
- 无匹配消费日志时返回 0。
- 单条日志倍率异常时不使整个查询失败，按倍率 1 计算。

## 测试

后端回归测试覆盖：

- 倍率 1 的消费日志保持原额度。
- 倍率 0.23 的消费日志按除法还原。
- 倍率缺失、零值和负值按 1 回退。
- 时间、用户、模型、渠道和分组筛选生效。
- 超级管理员响应包含 `actual_quota`，普通管理员响应不包含。

前端测试覆盖：

- 超级管理员在“期间收益”后看到“实际额度消耗”。
- 普通管理员看不到该指标。
- API 类型和默认统计值支持 `actual_quota`。

## 非目标

- 不计算净消耗或退款抵扣。
- 不计算利润、毛利率或渠道成本。
- 不修改日志详情表格中的单条日志展示。
- 不新增数据库字段或后台回填任务。
